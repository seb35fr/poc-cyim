Résumé en dix lignes#

statistics est une SPA Vue 3 autonome, en lecture seule, qui produit un tableau de bord de statistiques par congrès. Elle n'a ni backend propre, ni base de données : elle agrège deux sources existantes — le gateway Apollo GraphQL (délégués, sessions, config événement, noms de zones) et 5 index Elasticsearch alimentés par Flink (scans sur site, vues live, vues replay). L'intégralité des statistiques est calculée dans le navigateur par des fonctions pures (src/utils/compute*.js), puis rendue par Chart.js.

Le PoC assume trois écarts majeurs au standard CYIM, tous liés à sa vocation de prototype : JavaScript au lieu de TypeScript, aucun framework UI (@platform/common-ui absent, CSS maison), et surtout un accès Elasticsearch direct depuis le navigateur avec un token Bearer stocké dans .env — sans Keycloak ni Cerbos. Ces trois points sont le cœur du chantier de pérennisation.

01

Architecture & runtime

1.1 Positionnement#

statistics est une application front autonome, hors du monorepo applicatif congress/microservices/. Elle se branche en lecture seule sur l'infrastructure de production existante et n'écrit jamais : aucune mutation GraphQL, aucun _update Elasticsearch, aucun événement Kafka produit.

Conséquences directes de ce positionnement :

  • Aucun déploiement backend n'est requis pour la faire fonctionner — c'est ce qui a permis de la livrer vite.
  • Aucune donnée n'est persistée : chaque chargement de page refait l'intégralité des requêtes. Il n'y a ni cache serveur, ni cache navigateur applicatif (seul le cache HTTP standard s'applique).
  • Le navigateur porte toute la charge de calcul. Sur un congrès de 15 000 délégués et 100 000 scans, c'est le poste de travail de l'utilisateur qui agrège.

Le PoC recouvre fonctionnellement le microservice congress/microservices/xlsx-stats sur le périmètre des scans sur site (audience par session, check-in d'entrée, accès aux zones) : les deux lisent les mêmes index Elasticsearch.

1.4 Bootstrap — ce qui s'exécute au démarrage#

src/main.js (54 lignes) fait exactement quatre choses, dans cet ordre :

  1. Enregistrement Chart.js — ArcElement, BarElement, LineElement, PointElement, CategoryScale, LinearScale, Tooltip, Legend, Filler + le plugin chartjs-plugin-datalabels.
  2. Défauts Chart.js — police Poppins 14 px, et surtout Chart.defaults.plugins.datalabels.display = false : les datalabels sont désactivés globalement et réactivés au cas par cas. Certains graphiques contournent ce défaut par des plugins Chart.js locaux qui dessinent les totaux en bout de barre.
  3. Routeur — deux routes seulement (cf. §1.6).
  4. Montage — createApp(App).use(router).use(i18n).mount("#app").

Il n'y a ni Pinia, ni garde de route, ni initialisation d'authentification : le token est lu directement depuis import.meta.env au premier appel réseau.

2.1 GraphQL — src/api/graphql.js#

Endpoint et instrumentation#

const GRAPHQL_URL = import.meta.env.DEV ? "/api/graphql" : import.meta.env.VITE_GRAPHQL_URL;
const AUTH_TOKEN  = import.meta.env.VITE_AUTH_TOKEN;

En développement, les appels passent par le proxy Vite /api/graphql (réécrit vers l'origine de VITE_GRAPHQL_URL) ; en production, l'URL est appelée directement — ce qui suppose que le gateway autorise l'origine du dashboard en CORS.

Toutes les requêtes traversent le wrapper gqlFetch(query, variables), qui n'est pas un client GraphQL mais un fetch instrumenté. Il apporte quatre choses :

  1. Nom d'opération extrait de la requête (query GetSessions(...) → GetSessions) pour identifier la requête fautive dans les logs sans dumper le corps.
  2. Mesure du temps écoulé sur chaque appel, journalisée en cas d'erreur.
  3. Détection de délai dépassé — HTTP 504/408/524, message serveur contenant timeout|timed out|deadline, ou codes d'extension GRAPHQL_TIMEOUT, REQUEST_TIMEOUT, GATEWAY_TIMEOUT. Un TypeError: Failed to fetch survenu après 10 s est étiqueté « probable timeout ».
  4. Avertissement sur requête lente au-delà de SLOW_QUERY_THRESHOLD_MS (5 000 ms).

Ce dispositif existe parce que la pagination des délégués sur les gros congrès mourait silencieusement : sans nom d'opération ni durée, une page perdue était indétectable.

2.2 Elasticsearch — src/api/elasticsearch.js#

Accès#

const ES_BASE = import.meta.env.DEV ? "/api/es" : import.meta.env.VITE_ES_URL;
const BATCH_SIZE = 2000;

Le client est un fetch brut de 99 lignes vers POST /{index}/_search. Aucun en-tête d'authentification n'est envoyé — le cluster n'en a pas (identique à xlsx-stats/datasources/els.js, qui se connecte par un simple new Client({ node: process.env.ES_API })).

En développement, le proxy Vite /api/es évite le CORS et garde l'IP interne hors du navigateur. En production, ce proxy n'a pas d'équivalent : c'est le point de blocage principal du passage en production (cf. 09 — Dette technique).

Pagination#

fetchAllHits(index, query, onProgress) fait du search_after sur _id décroissant, par lots de 2 000, jusqu'à obtenir un lot incomplet. Il n'y a ni Point-in-Time, ni slice : la pagination est séquentielle, et une écriture concurrente pendant le parcours peut théoriquement décaler le curseur.

Toutes les requêtes filtrent sur un unique terme :

{ "term": { "congress_id.keyword": "<eventId>" } }

Même logique pour la durée (view_duration ∥ duration ∥ live_duration / vod_duration), l'origine (origin ∥ platform ∥ source ∥ device) et la fin de session (six candidats). Cette cascade de replis est une dette assumée : elle devrait disparaître au profit d'un mapping typé côté Flink.

Champs spécifiques :

  • Live : channel_id, channel_name (libellé de chaîne de diffusion, repli « Chaîne N » trié par volume).
  • Replay : media_id, presentation_id, presentation_title (granularité VOD).

Priorité du type de session#

Le sessionType est toujours résolu dans cet ordre :

s.session_type  →  s.sessionType  →  session GraphQL .type

Le champ Elasticsearch session_type est prioritaire car il vient de events.category côté SI-views — la même source que l'export xlsx-stats. Le type du nœud événement GraphQL n'est que le discriminant générique (« SESSION »), trop large pour être exploitable ; il n'est gardé qu'en dernier recours. Cette priorité a déjà été inversée par erreur deux fois (une fois sur les indicateurs, une fois sur le filtre des exports) : ne pas y toucher.

03

Modèle de calcul

Toute la couche de calcul vit dans src/utils/ et n'importe pas Vue. Ce sont des fonctions pures : mêmes entrées → mêmes sorties, aucun état, aucun effet de bord (à deux exceptions près, cf. 01 — Architecture §1.2).

C'est la partie du PoC qui porte la valeur métier, et aucune ligne n'est couverte par un test.

3.1 computeStats.js — statistiques d'inscription#

Signature et évaluation paresseuse#

computeAllStats(delegates, mobileAppId = null, dateRange = null)

La fonction ne calcule rien à l'appel. Elle retourne un objet dont les huit sections sont des accesseurs (get) mémoïsés par fermeture :

get global()       { if (!_global) _global = computeGlobal(delegates, mobileAppId, inRange); return _global; }
get demographics() { … }   get registrations() { … }   get temporal() { … }
get checkinFlow()  { … }   get badges() { … }          get onboarding() { … }   get mobileApp() { … }

Pourquoi : avant ce découpage, computeAllStats était une fonction monolithique de ~450 lignes qui calculait les huit sections en un passage. Chaque clic de filtre croisé recalculait tout, y compris les blocs que l'onglet courant n'affiche pas (l'onglet Démographie recalculait le temporel et les badges pour rien). Un onglet consomme typiquement 2 à 3 sections sur 8 : le gain est direct sur les événements de plus de 5 000 délégués.

Limite : la mémoïsation est par instance. Un nouveau filtre croisé produit un nouvel objet stats, donc un recalcul complet des sections consultées. Il n'y a pas de mémoïsation inter-clics.

Contenu des huit sections#

demographicscomputeDemographics(delegates)pays, uniqueCountries, continents, genre, professions, qualifications, civilités, sociétés

Les sections sont strictement indépendantes — aucune ne lit le résultat d'une autre. Là où un scalaire est nécessaire dans deux sections (totalBadgesDelivered par exemple), il est recalculé localement : une boucle O(n) supplémentaire est négligeable face au coût d'un bloc entier, et cela garantit qu'aucun accesseur ne déclenche en cascade le calcul d'un autre.

Portée du paramètre dateRange#

dateRange est converti une fois en prédicat par makeInRange() (utils/dateRange.js) puis injecté dans deux sections seulement : computeGlobal (pour checkedInCount) et computeCheckinFlow.

Les sections registrations (createdAt), badges (deliveredAt), onboarding, demographics et temporal ignorent le filtre date. C'est un choix délibéré, détaillé dans 04 — État & filtres §4.3.

Convention de valeur manquante#

groupBy() remplace une clé nulle par la chaîne littérale "Non renseigne" (sans accent, telle qu'écrite dans le code). Les catégories dérivées sont produites en français canonique ("Hommes", "Femmes", "Autre", "Tous les jours"), puis traduites à l'affichage par i18n/labels.js. La couche calcul reste ainsi indépendante de la locale — mais cela impose aux filtres croisés de comparer sur la valeur localisée ou de conserver la valeur brute comme étiquette (cf. 05 — Interface).

3.3 Jointures#

viewerJoin.js — Elasticsearch ↔ délégué#

Le user_id des index live et replay est un identifiant Keycloak, pas un delegate.id. La jointure côté navigateur reconstitue le lien via deux sources, exactement comme la requête contactByAccountId du service contacts :

#CheminCondition
1contact.emailAddresses[].source.idsource.type === "ACCOUNT"
2contact.externalIds[].valuetype === "/kc"

La source 2 est indispensable : elle capte les délégués dont le compte Keycloak n'est pas matérialisé dans emailAddresses. Sans elle, la couverture de jointure chute et des inscrits légitimes apparaissent comme « non reconnus ».

Un contact peut avoir plusieurs adresses e-mail, chacune liée à un compte Keycloak distinct : getKeycloakIds(delegate) collecte tous les identifiants et le délégué est indexé sous chacun d'eux. En cas de collision (deux délégués partageant un compte — anomalie de données), c'est le premier écrit qui gagne.

buildDelegateLookup(delegates) produit une Map<keycloakId, { checkedIn, delegate }>. Chaque hit Elasticsearch tombe alors dans l'une de trois catégories :

  • getKeycloakId(d) / getKeycloakIds(d).

Scans ↔ délégué#

Les trois index de scans portent directement le delegate.id MongoDB : aucune traduction n'est nécessaire. La jointure sert uniquement à enrichir (nom, e-mail, type de badge) et à récupérer les lignes orphelines — cf. §3.4.

3.4 Ré-association QR#

Le problème#

Côté Flink (stats_room_scans.sql), le QR scanné est résolu en délégué via le resolver event(id).registrationByBadgeQRCode(qrCode). Ce resolver (registration-badges/server/schemas/index.ts) applique decodeURI(qrCode), parse le résultat en chaîne de requête, puis :

  • si un paramètre d (delegateId) est présent → rapprochement sur { delegateId, eventId } ;
  • sinon → rapprochement sur le champ littéral { eventId, qrCode }.

Les badges réellement générés et finalisés (avec retrievalCode et storage en base) sont rapprochés. Les badges non générés, périmés, ou créés après le scan (n'ayant qu'un qrCode) retombent en échec.

Confirmé en production par comparaison de deux instantanés GraphQL du même délégué : le badge existe bien dans delegate.badges[], mais registration.badge est résolu de façon intermittente (null puis objet). Ce n'est donc pas une divergence de valeur — la donnée est correcte, c'est le timing de la recherche ponctuelle de Flink qui échoue. La conséquence diffère selon le type de jointure SQL :

IndexJointureConséquence
checkin, zoneLEFT JOINdelegate_id = '-' → récupérable
audienceINNER JOINligne absente de l'index → irrécupérable

La solution — sans aucun appel réseau#

Puisque le badge et son QR sont déjà chargés dans la population de délégués, le rattachement se refait côté navigateur.

buildQrDelegateLookup(delegates) construit une Map indexée de deux façons :

  • par QR — pour chaque badge, qrCode.value et qrCode.decodedValue, chacun sous plusieurs clés normalisées ;
  • par delegate.id — pour enrichir les scans déjà rapprochés.

La normalisation (qrKeys) génère deux clés candidates, de la plus spécifique à la plus tolérante :

CléTransformationTolère
soupletrim() + minusculesespaces en bordure, casse
stricteminuscules + suppression de tout caractère non alphanumériqueespaces internes, préfixe ponctué ("ER "), casse

La charge utile en base32 reste discriminante, donc aucune collision en pratique. Les mêmes clés sont utilisées des deux côtés (indexation des badges et recherche du scan), ce qui garantit la cohérence.

Le lookup est construit dans StatisticsView sur la population complète — délibérément pas filtrée par type de badge : la récupération d'un scan ne doit pas dépendre de l'état d'un filtre d'affichage.

Deux passes ensuite :

PasseCibleAction
recoverDelegateIds()scans à delegateId = '-' ou nullrapproche via raw_qr_code, pose scan.recovered = true
enrichFromLookup()scans à delegateId réelcomplète fullName, email, badgeType, badgeId si l'ES les laisse vides

Le piège du placeholder '-' : les lignes non rapprochées par Flink écrivent le caractère littéral '-' (et non une chaîne vide) dans user_email, user_fullName, etc. — conséquence du CASE WHEN … ELSE '-' du SQL. isBlankField(v) traite donc '', '-' et '—' comme vides. Sans cela, l'enrichissement de l'e-mail ne se déclenchait jamais.

L'enrichissement est non destructif : une vraie valeur Elasticsearch n'est jamais écrasée. Chaque champ enrichi porte un drapeau (fullNameEnriched, emailEnriched, badgeTypeEnriched, badgeIdEnriched) qui alimente le surlignage vert des cellules dans l'onglet Scans QR. Le fullName reconstitué prend la forme givenName familyName (delegateId) — la même que celle écrite par Flink pour les lignes rapprochées, par souci de cohérence des tableaux et des exports.

Portée et transparence#

Les scans récupérés comptent normalement partout : délégués uniques par jour, engagement, top sessions, cartes géographiques, tous les exports, export Markdown et dump JSON. Les compteurs global.recoveredScans et global.unmatchedScans sont affichés dans l'onglet Scans QR (« X ré-associés · Y restants non associés »), avec un filtre par QR et une modale d'inspection ligne par ligne.

Limites résiduelles : l'audience en salle reste irrécupérable (INNER JOIN), et si le scanner émet un QR réellement différent de value et decodedValue, le scan reste orphelin.

3.5 participation.js — le KPI « Total participants »#

computeParticipation(delegates, liveItems, replayItems, { datasetLabel, dateRange }) produit la photo dédoublonnée de qui a réellement participé. La règle : un délégué compte une seule fois, et la présence physique absorbe toute consommation à distance.

total = checkedIn + liveOnly + both + replayOnly

La présence physique est ensuite décomposée en quatre sous-groupes disjoints dont la somme vaut exactement checkedIn :

Sous-groupeDéfinition
checkedInOnlyprésent, aucune consommation à distance
checkedInLiveprésent + live seul (pas de replay)
checkedInReplayprésent + replay seul (pas de live)
checkedInLiveReplayprésent + live et replay

Les participants à distance (jamais présents physiquement) se répartissent en liveOnly, both et replayOnly.

La fonction retourne les Set<delegate.id> de chaque composante et un objet counts. Quand dateRange est fourni, le check-in physique est filtré sur checkedInDate ; les items live et replay sont, eux, déjà filtrés en amont par leurs compute* respectifs.

C'est la source unique de l'onglet Vue d'ensemble et de la section « Total participants » de l'export Markdown — aucune duplication de cette logique ailleurs.

3.6 computeLiveStats.js / computeReplayStats.js#

Même forme : compute*Stats(hits, sessionMap, dateRange) normalise les hits Elasticsearch, les enrichit via la sessionMap GraphQL (titre, type, début, fin, durée), filtre par date, puis agrège.

La différence essentielle est la date de référence :

Champ de filtrage et de regroupementSens
LivesessionEnd (repli sessionStart, puis timestamp)date de diffusion
Replaytimestampdate de visionnage, potentiellement très éloignée de la session

Pour le replay, il n'y a délibérément aucun repli sur session_start : cela reviendrait à regrouper par date de session au lieu de date de consultation, ce qui viderait l'indicateur de son sens.

Le repli du live sur sessionEnd s'explique par l'absence d'horodatage de visionnage fiable dans l'index live. C'est aussi pourquoi le filtre date global est inactif par défaut : sans cela, une session sans sessionEnd, sessionStart ni timestamp serait exclue et le live tomberait à zéro.

Le libellé de chaîne de diffusion vient de channel_name (exposé par l'index), avec un repli Chaîne N trié par volume décroissant.

4.1 Le patron du « lift » — où vit l'état#

Il n'y a pas de bibliothèque de gestion d'état : ni Pinia, ni Vuex. L'état réactif vit dans des composables à base de ref / computed / readonly.

La règle structurante du PoC : tout composable porteur d'un setInterval ou d'un appel réseau est instancié une seule fois, dans StatisticsView.vue, puis propagé aux onglets par props.

├── statsApi        = useStatistics(eventId)
├── liveApi         = useLive(eventId, { getDateRange })
├── replayApi       = useReplay(eventId, { getDateRange })

├── badgeFilter     = useBadgeTypeFilter(() => delegates, () => compareDelegates)

4.2 Filtre type de badge#

Multi-sélection sur la population de délégués. Le type de badge d'un délégué est déterminé par delegateBadgeType(d) : premier badge en base, à défaut première inscription.

Propagation : les onglets d'inscription reçoivent pageDelegates / pageCompareDelegates (déjà filtrés) ; les scans sont filtrés sur leur champ badge_type ; Live et Replay filtrent leur population de jointure.

Le composant <BadgeTypeFilter> ne porte que l'interface — l'état vit dans le composable, ce qui garantit la persistance d'un onglet à l'autre.

4.3 Filtre plage de dates#

C'est le mécanisme le plus subtil du PoC, et celui qu'il faut comprendre avant de le modifier.

Portée volontairement restreinte#

Le filtre s'applique uniquement aux statistiques datées par une activité de présence ou de consultation :

Appliqué àChamp de référence
check-in physiquecheckedInDate
vues livesessionEnd (date de diffusion)
vues replaytimestamp (date de visionnage)
scans QR (salle, zone, entrée)timestamp

Non appliqué aux inscriptions (createdAt), aux badges délivrés (deliveredAt), à l'onboarding, à la démographie, ni aux répartitions par type ou catégorie.

Le raisonnement : restreindre une plage de dates répond à la question « que s'est-il passé pendant ces journées ? ». Le nombre d'inscrits ou la répartition géographique d'un congrès ne sont pas des événements datés dans cette fenêtre — les filtrer produirait des chiffres trompeurs.

Le mécanisme de neutralisation par défaut#

Les bornes par défaut sont début = inscription la plus ancienne (le createdAt minimum sur les deux événements en mode comparaison) et fin = aujourd'hui. Mais tant que l'utilisateur n'a modifié aucune borne, isDefault vaut true et :

const effectiveDateRange = computed(() => (isDateDefault.value ? null : dateRange.value));

→ null est transmis, donc aucun filtrage n'a lieu.

Pourquoi ce garde est indispensable : les items Elasticsearch n'ont pas toujours un horodatage de visionnage fiable. Le regroupement retombe alors sur session_start ou session_end, qui peut tomber hors de la plage par défaut. Sans neutralisation, ouvrir le dashboard afficherait un Live à zéro — un faux négatif spectaculaire. Le filtre ne s'active donc qu'après une action explicite de l'utilisateur.

Ce garde est un contournement d'un défaut de qualité de données amont, pas un choix d'ergonomie. Il disparaîtra quand le mapping Elasticsearch exposera un horodatage de vue typé et systématique.

Propagation#

  • L'état est propre à l'onglet et perdu au changement d'onglet : le v-if détruit et recrée le composant. C'est assumé — les filtres globaux, eux, persistent.
  • Un libellé traduit doit être comparé sur sa valeur localisée. Quand une catégorie est produite en français canonique par computeStats puis traduite à l'affichage, le prédicat de filtre doit comparer la valeur localisée — ou conserver la valeur brute comme étiquette et comparer le brut. À unifier lors du portage vers stats-core — c'est un cas de test de non-régression à écrire explicitement.

7.3 Total participants (dédoublonné)#

L'indicateur central du bilan. Un délégué compte une seule fois, et la présence physique absorbe toute consommation à distance.

total = checkedIn + liveOnly + both + replayOnly
ComposanteDéfinition

La composante physique est en outre décomposée en quatre sous-groupes disjoints dont la somme vaut exactement checkedIn : checkedInOnly, checkedInLive (live seul), checkedInReplay (replay seul), checkedInLiveReplay (les deux).

Comprendre audienceUniqueDelegateSessions (« vues en salle »)#

C'est la mesure de l'audience réelle des conférences. Les multi-scans d'une même session par la même personne sont dédoublonnés, mais un délégué présent à N sessions compte N fois.

Alice : sessions A, B, C   →  3
Bob   : session A (scanné 2×) →  1
                              ─────
« vues en salle »            =  4      délégués uniques en salle = 2

Confondre les deux est l'erreur d'interprétation la plus fréquente sur cet onglet.

Sens de passage#

direction est normalisé en in / out / unknown par correspondance de sous-chaîne (in*, entr* → in ; out*, sort* → out). Tout libellé inattendu tombe en unknown et reste comptabilisé dans les volumes.

Ré-association#

recoveredScans = scans dont le delegate_id valait '-' mais dont le QR a été rattaché côté navigateur ; unmatchedScans = scans restant réellement orphelins (badge d'un autre événement, badge de test, QR illisible). Les scans récupérés comptent normalement dans tous les indicateurs. Voir 03 — Modèle de calcul §3.4.

9.1 Sécurité & conformité#

🔴 D1 — Elasticsearch exposé au navigateur, sans authentification#

/api/es/{index}/_search transfère la requête telle quelle. Aucune authentification, aucune liste blanche d'index, aucune limitation de débit. Le cluster lui-même n'a pas d'authentification (new Client({ node: process.env.ES_API }) dans xlsx-stats/datasources/els.js).

Conséquence : toute personne atteignant le proxy peut interroger n'importe quel index du cluster, y compris hors périmètre congrès.

Traité par : L1 (accès ES côté serveur) + L3 (API d'agrégation).

🔴 D2 — Token Bearer dans le bundle JavaScript#

VITE_AUTH_TOKEN est injecté à la compilation, donc lisible dans le fichier .js livré. C'est un token de session utilisateur réelle, avec ses droits complets. Il expire sans mécanisme de rafraîchissement.

Il n'y a ni Keycloak, ni garde de route, ni vérification de permission : quiconque a l'URL et un token voit toutes les données de l'événement.

Traité par : L2 (Keycloak + Cerbos).

🔴 D3 — Aucun masquage RGPD#

Le champ delegate.gdpr est récupéré mais jamais utilisé pour anonymiser. Le microservice xlsx-stats, dont ce PoC reprend le périmètre, remplaçait par *** les délégués sans consentement. Le dashboard affiche nom, e-mail et RPPS de tout le monde, et les exporte.

Aggravant : le dump JSON de l'export Markdown contient les délégués bruts, y compris les données de contact, et se retrouve téléchargé sur des postes puis potentiellement transmis à un service de LLM tiers.

Traité par : L3 (masquage côté serveur) + L7 (recette RGPD).

🟠 D4 — Aucun contrôle d'accès par événement#

L'eventId de l'URL n'est jamais confronté aux droits du porteur du token. Un utilisateur habilité sur un congrès peut lire les statistiques de n'importe quel autre en changeant l'URL.

Traité par : L2.

9.2 Architecture & données#

🔴 D5 — Aucun équivalent production du proxy /api/es#

Le proxy est un mécanisme du serveur de développement Vite. En production, il faudrait exposer un /api/es côté nginx vers un cluster sans authentification — ce qui revient à publier D1.

Traité par : L1 + L3 (le proxy disparaît).

🟠 D6 — Tout chargé en mémoire navigateur#

Aucune agrégation serveur : le navigateur télécharge l'intégralité des délégués, scans, vues live et vues replay, puis calcule. Au-delà de ~100 000 scans, la mémoire et les computed deviennent le facteur limitant.

Traité par : L3 (agrégations size: 0 + terms / date_histogram / cardinality) + L7 (perf).

🟠 D7 — Agrégats backend existants non utilisés#

fetchMetrics est écrit mais jamais appelé. Le backend expose déjà totalDelegatesCount, checkedInCount, statuses, categories, types, companies, accessDays — que le PoC recalcule intégralement côté client.

Traité par : L3.

🟠 D8 — Ré-association QR faite côté client#

Le rattachement des scans orphelins est un contournement client d'un défaut du pipeline Flink (cf. 03 §3.4). Il fonctionne, il est documenté, mais :

  • il ne bénéficie pas aux autres consommateurs des mêmes index (xlsx-stats, exports historiques) ;
  • l'audience en salle reste irrécupérable (INNER JOIN côté Flink) ;
  • le vrai correctif est en amont — rendre la résolution registrationByBadgeQRCode déterministe, ou rejouer l'enrichissement.

Traité par : L3 (centralisation côté serveur). Le correctif amont Flink reste un chantier distinct.

🟠 D9 — Mapping Elasticsearch non stabilisé#

Le code compense l'instabilité du mapping par des cascades de replis : onze champs candidats pour l'horodatage live/replay, quatre pour la durée, quatre pour l'origine, six pour la fin de session. Plus deux heuristiques fragiles :

HeuristiqueRisque
ms vs secondes (toEpochMs, seuil < 10¹²)casse si Flink change la forme
direction par sous-chaîne (in*/entr*/out*/sort*)tout nouveau libellé tombe en unknown

Correctif de fond : champs date typés et enum IN\|OUT\|UNKNOWN côté Flink.

Traité par : L3 (normalisation côté serveur), correctif amont Flink hors périmètre.

🟡 D10 — Noms d'index codés en dur et incohérents#

audience utilise des tirets, checkin et zone des underscores. Aucun alias versionné : un renommage côté cluster casse le dashboard silencieusement.

Traité par : L1 (alias versionné côté serveur).

🟡 D11 — Pagination Elasticsearch séquentielle sans PIT#

search_after sur _id décroissant, sans Point-in-Time ni slice. Une écriture concurrente pendant le parcours peut théoriquement décaler le curseur.

Traité par : L3.

🟡 D12 — Aucun rafraîchissement incrémental#

Le rafraîchissement recharge tout. Pistes : PIT + timestamp > last_seen, ou SSE depuis un backend écoutant cyim.webhooks.

Traité par : L7.

🟡 D13 — Filtre des comptes internes incohérent#

fetchLiveViews et fetchReplayViews excluent *@cyim.com ; les trois index de scans non. Un scan par un compte interne compte dans la présence sur site.

Traité par : L3 (règle unique côté serveur).
